# План MVP: фото предзаказа → счёт в 1С (№16 ↔ «Бухгалтерия для Казахстана» 3.0.75.1)

Дата: 30.10.2026. Основа: `docs/1C_INTEGRATION_PLAN.md`,
`docs/1C_EXTENSION_SPEC.md`. Статус: серверная часть MVP-1…MVP-3 (M1–M4)
выполнена; 1С-часть ждёт тестовой базы.

## 1. Цель MVP

Один реальный чек проходит весь путь **без ручного ввода строк**:

```text
1С: новый незаписанный счёт → «Обработать фото»
  → браузер: фото → OCR → проверка → выбор номенклатуры 1С
  → «Подтвердить для 1С»
  → 1С: «Получить результат» → форма заполнена (без записи)
  → оператор проверяет и записывает
  → 1С отправляет «применено»; на странице виден статус
```

MVP считается достигнутым, когда это выполняется на **тестовой копии** базы
«Алатау» с реальным чеком, без дублей и без ручной правки сумм.

## 2. Границы MVP

### 2.1. Входит в MVP

| Область | Минимум |
|---|---|
| Веб-сервер | `POST /tasks`, `GET /tasks/{id}`, `POST /tasks/{id}/photos`, `POST /tasks/{id}/confirm`, `GET /tasks/{id}/result`, `GET /tasks/{id}/result.xml`, `POST /tasks/{id}/document-link`, `POST /tasks/{id}/import-receipt`; без сетевой аутентификации (доверенная сеть) |
| Страница оператора | `/tasks/{id}/ui`: загрузка фото в задание, проверка чека, выбор/подтверждение номенклатуры, кнопка «Подтвердить для 1С», статус задания |
| Снимок для 1С | JSON 1.1: строки `source/target/allowed_targets`, версия, checksum, суммы по чеку (цена с НДС, 2 знака, `ROUND_HALF_UP`) |
| 1С | расширение формы счёта: команды «Обработать фото»/«Получить результат», видимость по наличию строк, HTTP без авторизации, заполнение ТЧ без записи, защита от повторной заливки, квитанция `applied` после записи, постоянная связь |
| Остатки | проверка текущего остатка по организации/складу для выбранных карточек; предупреждение о дефиците и явное подтверждение продолжения |
| Надёжность | идемпотентность `POST /tasks`, повторов `result`/`confirm`, квитанций; восстановление заданий после рестарта Python |
| Приёмка | сквозной сценарий на тестовой базе + чек-лист из `1C_INTEGRATION_PLAN.md` §9 |

### 2.2. НЕ входит в MVP (следующие этапы)

- Использование XML в расширении 1С (основной формат — JSON; серверный
  `result.xml` готов как альтернатива).
- Несколько фото на одно задание.
- Автоматическое деление строки между карточками.
- Полный сценарий «планировать закупку» (в MVP — предупреждение + «выставить
  с дефицитом»/ручная замена; закупка — после пилота).
- Восстановление незаписанного задания по ID в интерфейсе 1С (можно вручную
  через `GET /tasks/{id}`).
- Обучение связям из 1С, PDF счёта в 1С, HTTPS, многопользовательская
  авторизация сайта, несколько процессов сервера.
- Автоматическая установка/публикация расширения.

Порядок можно сдвигать: MVP-4…MVP-7 требуют тестовой 1С; MVP-1…MVP-3
делаются сразу и проверяются без 1С.

Реализация MVP-1: `App/exchange/multipart.py`; маршруты
`POST /tasks/{id}/photos` (поле `file`, одно фото на задание),
`GET /tasks/{id}/ui` (страница оператора) и `GET /tasks/{id}/ui/state`;
в `App/web/app.js` — распознавание адреса задания, загрузка через задание,
восстановление по `job_id`, бейдж «Задание 1С» в шапке.

Реализация MVP-2: `App/exchange/contract.py` — JSON 1.1, канонический
checksum (SHA-256 без поля `checksum`), `input_revision` (отпечаток чека,
связи, подписи справочника и реквизитов); `ExchangeStore.confirm()` пишет
`web_outputs/exchange/<task_id>/result-vN.json` и хранит метаданные версии;
`POST /tasks/{id}/confirm` отклоняет неготовый счёт (409 с причинами) и
повтор с той же ревизией идемпотентен; `GET /tasks/{id}/result` отдаёт
202 до подтверждения, 409 после правок/при смене входных данных и 200 с
неизменяемым снимком. `POST /api/jobs/{id}/edits` и сохранение связей
помечают подтверждение устаревшим. В блоке счёта — кнопка «Подтвердить
для 1С» и статус версии; после подтверждения правки разрешены, но требуют
повторного подтверждения.

Реализация MVP-3: `POST /tasks/{id}/document-link` привязывает UUID
записанного (в том числе пустого) счёта, повтор безопасен, другой UUID —
409; `POST /tasks/{id}/import-receipt` принимает `applied`/`error`,
проверяет базу/форму, версию, checksum и документ, идемпотентен по
`operation_id` (то же тело → 200, другое тело или другая операция после
применения → 409); `error` не привязывает документ и не меняет статус.
`GET /tasks/{id}/result.xml` отдаёт тот же зафиксированный снимок
(`TorgsoftInvoice schemaVersion="1.1"`; `conditions` — JSON-текст).
После `applied` задание терминально: повторное подтверждение отклоняется,
снимок остаётся доступным, последующие правки чека не отменяют отметку
применения. Привязка и квитанции сохраняются в `task.json` и переживают
рестарт. Тесты: `test_exchange_receipts.py`, `test_exchange_store.py`.
Структурная проверка и показ `stock_warnings` оператору — в MVP-5
(дефицит); сейчас квитанция сохраняет их как есть.

## 5. Критерии готовности MVP

1. Из 1С создаётся задание и открывается страница оператора.
2. Повтор «Обработать фото» открывает то же задание; второе не создаётся.
3. Фото распознаётся; строки проверяются и сопоставляются; «Подтвердить
   для 1С» доступно только для готового счёта.
4. После подтверждения снимок неизменяем; правка требует повторного
   подтверждения; `GET result` до этого → 409.
5. 1С заполняет форму **без записи**; повторное получение не дублирует
   строки; суммы строк и итог совпадают с чеком (НДС в цене, 2 знака).
6. Дефицит показывается с остатком и требует явного решения оператора.
7. После записи счёта связь сохранена, `applied` доставлен; сбой сети не
   создаёт дубль (повтор той же квитанции).
8. Пустой записанный счёт связывается без отметки «применено».
9. Сервер переживает рестарт: задание и подтверждение восстанавливаются.
10. Сквозной проход на тестовой базе 3.0.75.1 с реальным чеком.

## 6. Риски MVP и снижение

| Риск | Снижение |
|---|---|
| Нет доступа к 1С/метаданным | Серверная часть готова и проверена без 1С; для 1С нужна выгрузка конфигурации или разработчик на месте |
| Имена ТЧ/событий не совпадут с шаблонами №15 | Обследование релиза до кода; шаблоны — только основа |
| Расхождение цены/суммы из-за округления в 1С | В снимке `quantity/price/amount` decimal-строками; контроль суммы строки; допуск и явное сообщение |
| Дефицит/резервы считаются иначе | Проверка остатков в 1С по правилам релиза; Python остатки не подменяет |
| Потеря связи с незаписанной формой | `request_id`/`task_id` в реквизитах формы; ручное восстановление по `task_id` |
| Один процесс сервера | Не запускать `--workers`; реестр и блокировки process-local |
| Открытый сайт | API `/tasks/*` только по ключу; сайт — в доверенной LAN |

## Изменение от 31.10.2026

По прямому указанию пользователя отдельное подтверждение отменено.
GET result/result.xml автоматически фиксирует и возвращает сформированный
счёт, включая предложенные товары; готовность к обучению не требуется.
До формирования — 202. После правок следующий GET выдаёт новую версию.
Статус confirmed сохранён в контракте для совместимости и означает
техническую фиксацию версии, а не действие оператора. После applied
сохраняется прежний неизменяемый результат. Кнопка подтверждения скрыта.


## Уточнение налогового контракта от 31.10.2026

В обмене JSON/XML цены и суммы `items[].target` и `allowed_targets`
передаются **без НДС**, из исходных сумм строк электронного чека.
`prices_include_vat=false` и совместимый псевдоним `price_includes_vat=false`.
Ставка — `vat_rate`, сумма НДС — `vat_amount`; объект `totals` содержит
`amount_without_vat`, `vat`, `amount_with_vat`. Поле `total` сохраняет
полный итог с НДС. Строка НДС не является номенклатурой и в items не входит.
Услуга 5000 × 1 передаётся как 1 × 5000.00 без НДС.
Идентификаторы задания/запроса и кандидатов, target, allowed_targets
сохраняются. PDF по прежнему показывает цены с НДС. Клиент 1С должен
применять налог один раз, согласно флагу цены. Это уточнение заменяет
прежнее описание цен обмена с включённым НДС.


## Два режима получения — уточнение 01.11.2026

Автоматический показ счёта/PDF в браузере сохраняется. Правило автоматической
фиксации confirmed на GET от 31.10 отменено. Обычный GET result/result.xml
возвращает 202 до явного POST confirm, затем 200 confirmed. Ручной запрос
с allow_unconfirmed=1 выдаёт завершённый корректный черновик 200
ready_unconfirmed, ocr_complete=true; ни запрос, ни завершение OCR не
подтверждают его. Если веб-подтверждение уже есть, оба режима выдают
неизменяемый confirmed. Правка требует нового веб-подтверждения для
автоимпорта; ручной запрос может получить новую версию готового черновика.
Подтверждение не обучает связи автоматически. Цены обеих выдач без НДС;
request_id/task_id/source/target/allowed_targets/selection_policy сохранены.
Веб-кнопка «Подтвердить и передать в 1С» сохраняет текущий ручной выбор,
после HTTP 200 показывает сообщение под PDF с прокруткой и фокусом.
Полный аудит и проверки: docs/DUAL_MODE_EXCHANGE_2026-11-01.md.
