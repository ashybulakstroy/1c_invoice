## 1. Цель

Оператор в 1С открывает новый счёт на оплату покупателю, нажимает
«Обработать фото» — в браузере открывается веб-страница OCR-службы, где по
фото чека предзаказа Торгсофт собирается и подтверждается таблица товаров.
Оператор возвращается в 1С, нажимает «Получить результат» — открытая форма
счёта заполняется проверенными позициями, 1С сама выбирает номенклатуру по
актуальным остаткам и предупреждает о дефиците. Документ **не записывается
автоматически**: оператор смотрит и записывает штатной командой. После
успешной записи 1С сообщает OCR-службе статус `applied` и сохраняет
постоянную связь «задание ↔ документ».

Приоритет — работающий сквозной сценарий на реальных документах. Безопасность,
универсализация API и служебная обвязка — в конце, по остаточному принципу
(раздел 25 исходного ТЗ).

## 3. Разграничение сторон

**Сторона 1С (создаётся по этому ТЗ):**

- две команды в форме счёта и управление их видимостью;
- исходящий HTTP-транспорт к OCR API (без авторизации, доверенная сеть);
- идемпотентное создание задания (`request_id` формы) и получение результата;
- сверка `database_id`, `request_id`, версии результата и контрольная
  повторная проверка на повтор нажатия второй кнопки;
- выбор номенклатуры строго из подтверждённых вариантов по актуальным
  остаткам; расчёт дефицита в сопоставимых единицах;
- обязательное предупреждение о дефиците и три решения оператора;
- заполнение открытой формы **без автоматической записи**;
- сохранение постоянной связи и отметки применённой версии после записи;
- отправка квитанции `applied` после успешной записи (с повтором по тем же
  идентификаторам при сбое);
- повторная проверка остатков **только перед проведением** документа
  реализации/отгрузки — правилами конфигурации, не при записи счёта.

**Сторона 1С НЕ делает:**

- OCR, распознавание фото, классификацию «НДС/доставка/услуга»;
- ведение маппинга и пополнение подтверждённых соответствий (это веб-интерфейс);
- программное создание/запись/проведение документа счёта;
- редактирование типовой конфигурации;
- молчаливый подбор номенклатуры вне подтверждённого списка;
- деление одной исходной строки между несколькими карточками 1С
  (отключено до отдельного согласования);
- повторную проверку остатков при обычной записи счёта.

## 4. Сквозной сценарий (закреплён)

1. Оператор создаёт **новый незаписанный** счёт («Создать» → форма пуста,
   шапка может быть пустой). Предварительная запись пустого документа не
   требуется.
2. Нажимает «Обработать фото»: 1С создаёт `request_id` (UUID) в реквизитах
   формы **до** сетевого вызова, затем `POST /tasks` с `database_id` и
   `request_id` (без `document_uuid`). Получает `task_id` и `ui_url`,
   сохраняет их в реквизитах формы, открывает URL в браузере.
3. На странице оператор загружает фото, правит распознанные значения,
   выполняет сопоставление и нажимает подтверждение.
4. Нажимает «Получить результат» в 1С (можно до и после шага 3): пока
   трансформация не подтверждена — `HTTP 202`, форма не меняется; после
   подтверждения — `HTTP 200` с зафиксированным снимком версии.
5. 1С проверяет **все** строки и остатки, при дефиците показывает
   предупреждение и ждёт решения оператора (раздел 9), затем заполняет
   табличные части открытой формы. Запись документа не выполняется.
6. Оператор проверяет и жмёт штатную запись. Только после фактически
   успешной записи появляется `document_uuid`: 1С сохраняет постоянную
   связь, отметку версии и отправляет квитанцию `applied`.
7. Периодически: перед проведением файла реализации/отгрузки, созданного
   на основании счёта, выполняется штатная (и встраиваемая) повторная
   проверка наличия.

## 5. Две команды формы: видимость, доступность, защита от обхода

### 5.1. Состав расширения формы

Основная форма документа «Счёт на оплату покупателю»; конкретный объект
метаданных и названия табличных частей уточнить в релизе 3.0.75.1
(«товарные и сервисные» ТЧ далее — по факту). Добавить:

- команды `OCRОбработатьФото` («Обработать фото») и
  `OCRПолучитьРезультат` («Получить результат»), при необходимости группу
  `OCRГруппаКоманд`;
- реквизиты **формы**: `request_id`, `task_id`, `ui_url`, применённая
  версия (`applied_result_version`), checksum; и решения о дефиците по
  строкам. Ключ API и адрес сервера — **не** реквизиты формы.

### 5.2. Матрица видимости

Управлять **по фактическому наличию строк** в товарных и сервисных
табличных частях (включая одну вручную добавленную строку), а не по
признаку «записан» и не по заполненности шапки.

| Состояние формы | «Обработать фото» | «Получить результат» |
|---|---|---|
| Новый/записанный пустой счёт, задания нет | видна, доступна | видна, **недоступна** |
| Пустой счёт, задание создано (`task_id` есть) | видна; повтор открывает то же задание | видна и доступна; если не готово — сообщает статус без заполнения |
| Есть хотя бы одна строка (в т.ч. ручная) | **скрыта** | **скрыта** |
| Результат Python уже заполнил ТЧ, ещё не записан | **скрыта** | **скрыта** |
| Повторное открытие счёта со строками | **скрыта** | **скрыта** |
| Заполнена шапка, ТЧ пусты | видна, доступна | видна; доступность по наличию `task_id` |

Правила:

1. Пересчёт состояния — при открытии, после создания задания, после
   успешного импорта и после каждого ручного/штатного
   добавления/удаления строк. Удаление всех строк возвращает кнопки.
2. При заполненном счёте не оставлять пустые места под команды; штатные
   команды формы («Записать», печать) остаются без изменений.
3. Обработчики обеих команд проверяют пустоту ТЧ **на клиенте и на
   сервере** (двойная проверка, включая повторную серверную проверку сразу
   после сетевого запроса, перед любым изменением формы). При наличии
   строк — понятное сообщение и никакого изменения документа.
4. Скрытие кнопок не очищает `request_id`/`task_id` и не теряет задание.
5. Вторая кнопка не запускает OCR и не создаёт новое задание — только
   получает результат существующего. Первая — идемпотентна (тот же
   `request_id`).
6. Видимость/доступность — через `Элементы.<Имя>.Видимость` /
   `.Доступность`; синтаксис и события проверить в целевой форме.
7. Никакой автоматической записи/проведения при управлении кнопками.

### 5.3. Приёмка интерфейса (минимум)

На тестовой базе продемонстрировать: обе команды в новом незаписанном
пустом счёте; вторая недоступна без задания; становится доступной после
`POST /tasks`; повторная первая кнопка открывает прежнее задание; обе
скрыты после (а) заполнения из Python, (б) ручной строки, (в) повторного
открытия заполненного счёта; кнопки остаются при заполненной шапке;
после удаления всех строк видимость возвращается; повторный импорт не
дублирует строки; обход UI заблокирован серверной проверкой.

## 6. HTTP-контракт 1.1 с OCR API

Общие правила:

- Авторизация HTTP не используется (решение пользователя 30.10.2026);
  сервер и 1С работают в доверенной локальной сети.
- JSON UTF-8, `Content-Type: application/json`. Десятичные величины —
  **строки**; валюта `KZT`; выходные цены **включают НДС**; исходные
  цена/количество/сумма передаются отдельно от целевых.
- Повторы идемпотентны: вся аутентификация запроса — сочетание
  `database_id + request_id` (+`task_id`, `operation_id` для квитанций).
- Коды ответов трактовать по таблице; при `4xx/5xx` показывать понятный
  текст оператору, форму не менять.
- Рекомендуемый тайм-аут соединения — 20 с (как в примере `OCRClient.bsl`).

| Метод/адрес | Когда | Успех/особые коды |
|---|---|---|
| `POST /tasks` | «Обработать фото» (первичное и повторы) | `201` — новое; `200` — повтор той же пары `database_id+request_id` возвращает прежнее задание (в т.ч. конкурентные запросы); `409` — явный конфликт |
| `GET /tasks/{id}` | сверка состояния/привязки/прогресса | возвращает `state`: `waiting_photo`/`review`/`confirmed`/`applied` |
| `GET /tasks/{id}/result?database_id=…&request_id=…` | «Получить результат» | `202` — ещё не подтверждено (форму не менять, показать статус); `200` — подтверждённый зафиксированный снимок; `409` — результат изменён (нужно новое подтверждение) или параметры другой формы/базы |
| `GET /tasks/{id}/result.xml` | альтернативная выдача | корень `TorgsoftInvoice schemaVersion="1.1"`; семантика сумм как в JSON; `conditions` — JSON-текст внутри одноимённого элемента |
| `POST /tasks/{id}/document-link` | после записи **пустого** счёта либо для восстановления связи | связывает `document_uuid`, не меняет статус применения; повтор безопасен; привязка другого UUID/постороннего документа — `409` |
| `POST /tasks/{id}/import-receipt` | **только после успешной штатной записи** | поля: `database_id`, `request_id`, `document_uuid`, `operation_id` (UUID), `result_version`, `checksum`, `status: "applied"`, необязательные `document_number`, `message`, `stock_warnings`; повтор того же уведомления безопасен, изменение тела при том же `operation_id` — `409`; можно `status:"error"` при неуспешной записи |

Устаревший контракт 1.0 (`base_id`, `invoice_uuid`, статус `imported`) для
нового кода не использовать, поддержка минимумов — на стороне Python.

## 7. Снимок результата: поля и правила обращения

Ответ `200` `GET …/result` имеет `schema_version: "1.1"`,
`status: "confirmed"` и поля уровня документа:

- `task_id`, `database_id`, `request_id`, `document_uuid` (может быть `null`
  до записи — сохранять как есть), `result_version`, `revision`,
  `checksum`, `currency`, `prices_include_vat`, `date`,
  `source_order_number`, `vat_rate`, `vat_amount`, `total`;
- `items[]` — строки.

Скелет одной строки (имена полей приоритетны из этого перечня; при
расхождении с фактическим ответом службы источник истины — `/openapi.json`):

```json
{
  "row_id": "…",
  "photo_id": "…",
  "source": {"name": "…", "article": "…", "identity": "…", "quantity": "…", "price": "…", "amount": "…"},
  "target": {
    "code": "00000019603", "uuid": null, "catalog_id": "…",
    "name": "…", "service": false,
    "quantity_mode": "factor", "quantity_factor": "1",
    "quantity": "2", "price": "500", "amount": "1000"
  },
  "allowed_targets": [ /* тот же target + прочие подтверждённые варианты */ ],
  "selection_policy": "explicit"
}
```

Правила обращения:

1. **Сверка формы.** Сначала сверить `database_id` и `request_id` снимка с
   реквизитами формы (регистронезависимо для `request_id`). Чужой снимок —
   ошибка, форму не менять.
2. **`selection_policy`:** `explicit` — подтверждённый выбор оператора для
   этого чека: такое `target` менять по остаткам нельзя.
   `approved_alternatives` — применённое постоянное правило; приоритет всё
   равно у выбора оператора, сделанного в этом снимке.
3. **`allowed_targets`** содержит подтверждённые альтернативы одной
   исходной карточки/базы; сумма строки у всех одинакова. Предложения
   top10 без подтверждения в список не попадают.
4. **`target.code`** — текст из столбца «Код / Артикул» справочника 1С
   («Склад Алатау с артикулами»); ведущие нули значимы, код никогда не
   преобразовывать в число. В адаптере базы «Алатау» проверить по
   конфигурации, является ли поле кодом или артикулом, искать по нему,
   проверяя уникальность; одинаковые имена с разными кодами — разные
   карточки. **`target.uuid` в снимках всегда `null`** — UUID нет;
   `catalog_id` — внутренний ID поиска Python, **не** ссылка 1С. Тезисно:
   тождество карточки = код/артикул (+ при неоднозначности точное имя и
   единица); создавать карточку и брать «первую из нескольких» — нельзя.
5. **Количество:** `quantity_mode: "factor"` —
   `количество_1С = количество_Торгсофт × quantity_factor` (десятичная
   арифметика, коэффициент — уже подтверждённый для этого снимка);
   `quantity_mode: "service"` — брать подтверждённое количество услуги как
   есть, коэффициент не умножать. Вычисленные количества/цены/суммы
   округлять согласно политике 1С и свойствам документа; сумма строки
   должна остаться равной `target.amount`.
6. **`checksum`** — SHA-256 канонического UTF-8 JSON снимка (без поля
   `checksum`, ключи отсортированы, без пробелов-разделителей, без
   ASCII-экранирования). Пересчёт на стороне 1С необязателен: достаточно
   сохранить и вернуть как есть в квитанции.
7. **Повтор против версии.** Если код в форме совпадает с
   `result_version` снимка — ничего не заполнять (молча). Если в форме уже
   применена **другая** версия — явная ошибка «нужна сверка», не дописывание
   строк поверх. До первой применённой версии — заполнять.
8. Никаких частичных изменений при блокирующей ошибке хотя бы одной
   строки (раздел 9.3): прежние строки остаются как были.

## 8. Выбор номенклатуры и дефицит

### 8.1. Автоматический выбор (остатка хватает)

- Рассматриваются **только** варианты из `allowed_targets` с учётом
  условий применимости (`conditions`).
- Актуальные остатки по организации, складу, номенклатуре и
  характеристикам; смысл доступного количества уточнить в релизе
  (резервы и т.п.).
- Остатки приводятся к **общей единице исходного товара** по коэффициентам
  выбранных карточек; при равенстве — стабильный порядок (уточнить и
  зафиксировать в коде).
- Учитывать уже распределённое количество по всем строкам счёта: один
  остаток нельзя использовать дважды.
- Авто-деление строки на несколько карточек — отключено.

### 8.2. Дефицит: предупреждение, а не запрет

Если ни один вариант не покрывает строку, оператору **обязательно**
показывается: исходное название Торгсофт и позиция счёта; заказанное
количество и единица; рассматриваемые варианты 1С; доступный остаток
каждого; `дефицит = требуется − доступно` в сопоставимых единицах;
организация и склад проверки. Полное отсутствие — нулевой остаток и полный
дефицит. Оператор выбирает одно из действий:

1. **Выбрать другую номенклатуру** — из `allowed_targets` или штатным
   подбором. Карточка **вне подтверждённого списка** допускается только
   после явного подтверждения оператора как аналога **для этого счёта**;
   постоянный маппинг не менять. Проверить единицу/коэффициент/остаток
   заново.
2. **Планировать закупку** — фиксируется намерение; заказ поставщику не
   создаётся, поставка не считается гарантированной.
3. **Выставить счёт с дефицитом** — явное подтверждение; заполнение в
   полном заказанном количестве; цену/количество/сумму не подгонять;
   видимая отметка дефицита сохраняется до записи.

Решение — свойство конкретной строки и текущего остатка; хранить его в
контексте формы. Если выбрана закупка — фиксировать, что она не
подтверждена. Счёт является **не** резервированием товара.

### 8.3. Ошибки ≠ предупреждения

- Предупреждение (можно продолжить после решения): дефицит любого вида.
- Блокирующая ошибка импорта: нет корректной карточки 1С; нельзя
  подтвердить вручную выбранную; неизвестны обязательные единица или
  коэффициент; существенное расхождение сумм; незавершённая трансформация.
  Форму частично не менять.
- Если по строке всё-таки был применён не-подтверждённый вариант или
  изменились остатки между выбором и заполнением — сообщения 1С и
  предупреждения попадают в веб-интерфейс через необязательный
  `stock_warnings` квитанции: для каждой строки `row_id`,
  `nomenclature_uuid` выбранной карточки, `unit`, `required_quantity`,
  `available_quantity`, `deficit` (конечные decimal-строки; `required > 0`,
  `available >= 0`, `deficit = required − available`), `action` ∈
  `select_alternative` / `plan_purchase` / `accept_shortage`, необязательные
  `organization_uuid`, `warehouse_uuid`. Сервер проверяет структуру и
  арифметику; предупреждения — сведения, не блокировка.

### 8.4. Остатки и моменты проверок

- **Получение результата:** первичная проверка остатков (выбор варианта,
  предупреждение о дефиците).
- **Обычная запись счёта:** повторной проверки остатков **не** делать,
  даже если остатки изменились.
- **Проведение** документа реализации/отгрузки (в т.ч. созданного на
  основании счёта): повторная проверка текущего количества — до списания;
  встраиваемый контроль и точку определить по релизу. Подтверждение
  дефицита при выставлении счёта **не** разрешает провести отгрузку с
  минусом; действуют штатные ограничения конфигурации.

## 9. Хранение связи, отметка применения, квитанция

### 9.1. Серверные данные 1С

Создать объект для постоянной связи (например, регистр сведений; имя и
структуру согласовать в релизе). Минимум полей:

- `database_id`, `request_id`, `task_id`, `document_uuid`,
  `result_version` (применённая), `checksum`, отметка `applied_status`
  (`none`/`applied`/`error`), `operation_id` последней квитанции, даты,
  `document_number`.

Временные `request_id`/`task_id` остаются реквизитами формы до первой
записи. Если счёт записали пустым после создания задания — сохранить связь
`document-link`, но `applied` не отправлять.

### 9.2. Событие записи

После фактической успешной штатной записи (обработчик события записи
формы; конкретный обработчик уточнить в релизе; типовую конфигурацию не
менять):

1. записать в регистр связь + (`document_uuid`, `result_version`,
   `checksum`, `applied_status`);
2. сформировать `operation_id` (UUID) и отправить `POST …/import-receipt`
   с `status:"applied"` (+ `document_number`, `stock_warnings` при наличии);
3. потеря ответа не должна приводить к дубликату документа и не блокирует
   работу: операцию и тело квитанции хранить в 1С и повторять **те же**
   `operation_id` и тело после перезапуска, пока успешный ответ не
   получен. Ответ 1С — источник истины о записи; повтор квитанции
   безопасен по API;
4. при ошибке записи — `status:"error"` (не привязывает документ, не
   означает применение) либо не отправлять вообще; успешный статус
   ставить только после реальной записи.

### 9.3. Восстановление

- Записанный счёт: при повторном открытии связь восстанавливается из
  регистра (по `document_uuid`).
- Незаписанная закрытая форма: реквизиты формы могут быть потеряны; для
  первой версии достаточно ручной команды/обработки «Восстановить задание
  по ID» (ввод `task_id`), которая подтягивает состояние `GET /tasks/{id}`
  и восстанавливает привязку формы, без гарантии полного соответствия.

## 11. Технические требования к коду

- Язык — BSL, целевая платформа 8.3.23; без внешних компонент и COM.
- Десятичные величины из JSON хранить и сравнивать как строки в
  контракте; внутренние расчёты — десятичной арифметикой 1С с необходимой
  точностью/округлением по свойствам документа; сумма строки — контроль
  равенства `target.amount` (при расхождении — блокирующая ошибка).
- Поддержка UTF-8 encoding запросов/ответов; BOM не использовать.
- Пясуммирование/повторный импорт: без дописывания; все проверки перед
  изменением ТЧ формы.
- Стиль: комментарии на русском; устойчивый перенабор структуры примеров
  №15 приветствуется; модуль не полагается на глобальные сессии.
- Обработка сетевых ошибок/тайм-аутов: понятные сообщения; повтор — только
  идемпотентными средствами контракта.

## 13. Критерии приёмки (сквозной список)

1. Сквозной проход на тестовой базе: новый незаписанный счёт → фото в
   браузере → подтверждение → «Получить результат» → предупреждения
   (при необходимости) → заполненная форма → штатная запись → квитанция
   `applied` зафиксирована в Python.
2. Повторы и сбои не дублируют: повтор первой кнопки; повтор второй;
   загрузка пустого счёта; потеря ответа после записи (retry той же
   квитанции).
3. Видимость кнопок по матрице §5.2 во всех состояниях; серверная защита
   от обхода UI.
4. Принципы дефицита §8.2: без скрытых замен; явные три действия; отметка
   до записи.
5. Контроль версий: не дописывается к другой версии; 409 по
   модифицированному заданию выдаёт понятное сообщение.
6. Связь и восстановление: по записанному счёту связь восстанавливается;
   пустой счёт не даёт `applied`.
7. Остатки: запись счёта не проверяет; проведение отгрузки — проверяет
   (по правилам релиза).
8. Суммы: итог счёта равен подтверждённому итогу снимка (с учётом НДС
   в цене); расхождение — блокирующая ошибка без частичных изменений.
