Основная версия приложения — папка `App/` проекта №16.

Эти четыре области остаются за текущим `App/` проекта №16. Нельзя подменять их

Перенос не предполагает импорт соседнего проекта через `sys.path`: конечное
приложение должно работать самостоятельно, используя локальные модули и данные.

## 2. Целевой пользовательский путь

```text
Фото JPG/PNG/WEBP
  → текущие геометрия и RapidOCR проекта №16
  → текущий электронный чек и проверка названий, количеств, цен, НДС и итога
  → подтверждённый снимок чека с revision
  → выбор номенклатуры 1С, единиц и коэффициентов пересчёта
  → предпросмотр счёта и проверка его готовности
  → скачивание PDF счёта на оплату (и JSON модели документа)
```

Распознавание остаётся автоматическим. Спорные строки требуют участия оператора.
Совпадение суммы само по себе не означает подтверждения названий. Если чек уже
проверен, а все необходимые связи подтверждены, шаг трансформации может быть
автоматическим. Отправка документа в реальную 1С — последующий отдельный этап.

Веб-страница сохраняет текущие фото, разметку и электронный чек. После него
появляется блок «Счёт на оплату»: строки Торгсофт → строки 1С, выбор товара или
услуги, единицы, коэффициенты и количество, предупреждения, печатный предпросмотр
и кнопка скачивания. До готовности блок показывает конкретные причины отказа.
Нужны поля исправления даты/номера заказа и реквизитов документа: текущий API
редактирования чека ещё не поддерживает исправление шапки.

## 4. Граница данных: адаптер после подтверждения чека

Новый адаптер `App/invoicing/receipt_adapter.py` должен читать снимок текущего
результата, не менять его и не запускать OCR. Предлагаемый контракт:

| Поле №16 | Поле для генератора | Правило |
|---|---|---|
| `job_id`, `revision` | идентификатор/версия источника | сохранить в документе и ссылках скачивания |
| `rows[].row` | стабильный `items[].row_id` | не использовать изменяемое название в качестве ID |
| `rows[].name` | `items[].name`, подтверждённое имя | использовать текущее проверенное значение |
| `rows[].name_raw` | `items[].ocr_name` / evidence | оставить исходный текст отдельно; `receipt_names.torgsoft_name` адаптировать, чтобы он не предпочёл сырой OCR подтверждённому имени |
| `article`, `catalog_key` | идентичность источника Торгсофт | разрешать неоднозначность явно; ключ каталога Торгсофт не является ID 1С |
| `quantity`, `price`, `line_total` | количество, цена и сумма исходной строки | десятичные строки, расчёты через Decimal |
| `kind=product/service` | `items[]` | сохранить все оплачиваемые товарные строки и услуги |
| `kind=tax` | `vat_amount` | брать сумму строки, не сырое поле количества; отдельной товарной строкой в счёт повторно не добавлять |
| `kind=total` | не товарная позиция | исключить из items |
| `calculation.expected_total` | `total` | итог, прошедший текущую проверку; не вычислять вместо печатного итога |
| `date`, `order_number` | шапка документа | проверяемые значения из текущего чека/явных исправлений |

Вход в генерацию: `finalized=true`, актуальная `revision`,
`calculation.validation_status=match`, отсутствие непроверенных строк.
`can_finalize` означает возможность завершения проверки, а не её факт.
Проверки готовности счёта дополняют существующую валидацию чека, не заменяют её.

НДС распределяется по строкам один раз с точным сохранением общей суммы.
Нельзя автоматически начислять сверху 16%, если отдельного НДС в проверенном
чеке нет. Старый допуск `VAT_TOLERANCE=0.99` нельзя использовать для ослабления
строгой проверки электронного чека №16. Округление строк счёта и распределение
остатка должны сохранять итог до тиына и не скрывать реальные расхождения.

Цены продажи и суммы поступают только из текущего чека. Каталог 1С определяет
номенклатуру/единицы; подтверждённое преобразование определяет количество.
Цена строки 1С выводится из её суммы и нового количества. Ни остатки склада,
ни ранее выписанный счёт не являются источником текущей цены.

### Этап 3 — API и хранение счёта

Предлагаемые новые маршруты в текущем `App/web_server.py`:

- `GET /api/jobs/{id}/invoice` — модель и причины неготовности;
- `POST /api/jobs/{id}/invoice/preview` — предпросмотр без записи правил;
- `POST /api/jobs/{id}/invoice/selections` — сохранение явно выбранных связей;
- `GET /api/jobs/{id}/invoice.pdf?revision=...&token=...` — PDF актуального документа;
- отдельный поиск `/api/catalog-1c`, не менять смысл существующего `/api/catalog`.

Названия маршрутов — проектное предложение, сейчас они не реализованы.
Сохранять модель и выбранные связи рядом с заданием, атомарно, под блокировкой.
Токен документа должен учитывать снимок чека, связи, каталог и реквизиты.
После изменения источника аннулировать старую готовность и кеш PDF.
Как в №15, устаревшие revision/token возвращают 409. PDF недоступен до `ready`.
Сохранить восстановление завершённых заданий после рестарта и один серверный процесс.
