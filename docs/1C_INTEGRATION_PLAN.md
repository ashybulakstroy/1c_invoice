## 1. Как понята задача автоматизации

Система должна сократить ручной ввод при выставлении счёта на оплату:

```text
фото предзаказа Торгсофт (бумажный чек)
  → OCR и проверенный электронный чек            (№16, уже работает: App/)
  → оператор проверяет названия/количества/цены  (№16, уже работает)
  → сопоставление строк с номенклатурой 1С       (№16, уже работает: App/invoicing/)
  → ЗАФИКСИРОВАННЫЙ снимок результата для 1С     (новое: слой обмена)
  → 1С заполняет открытую форму счёта на оплату  (новое: расширение 1С)
  → оператор проверяет и записывает счёт штатно  (1С)
  → 1С сообщает «применено»                      (новое: квитанция)
```

Ключевые принципы (не меняются):

1. **Цены и суммы — только из текущего чека**, проверенного оператором.
   Каталог 1С даёт идентичность товара, единицу и подтверждённый коэффициент,
   но не цену продажи.
2. **1С не создаёт и не записывает документ сама** — только заполняет
   открытую форму. Запись/проведение — штатными командами пользователя.
3. **Сопоставление и подтверждение — в веб-интерфейсе №16**; 1С получает
   уже подтверждённый неизменяемый снимок.
4. **Остатки и дефицит проверяет 1С** при получении результата; дефицит —
   предупреждение с тремя решениями оператора, не автоматический отказ.
5. Повторные нажатия и сбои сети не дублируют строки и квитанции.

### 1.1. Как пользователь работает с решением

1. В 1С открывает **новый незаписанный** «Счёт на оплату покупателю».
2. Нажимает **«Обработать фото»** → открывается браузер со страницей задания
   (фото загружается на странице №16, как сейчас).
3. Проверяет распознанный чек, при необходимости правит строки; в блоке
   «Счёт на оплату» выбирает номенклатуру 1С и подтверждает связи.
4. Нажимает **«Подтвердить для 1С»** на странице — результат фиксируется.
5. Возвращается в 1С, нажимает **«Получить результат»** — форма счёта
   заполняется (без записи). При дефиците 1С показывает предупреждение и
   ждёт выбора: другая номенклатура / планировать закупку / выставить с
   дефицитом.
6. Проверяет счёт и записывает штатной кнопкой. 1С сохраняет связь и
   отправляет квитанцию `applied`; на странице №16 появляется статус
   «Применено в 1С».

## 3. Целевая архитектура

```text
 [1С: тонкий клиент]                       [Сервер Python №16, один процесс]
 Расширение формы счёта                    ┌──────────────────────────────────────┐
  • 2 команды + видимость                  │ App/web_server.py (HTTP)             │
  • OCRClient.bsl (транспорт) ── HTTP ───▶ │  /tasks/*  ← новый слой обмена        │
  • регистр связи и применений             │      │                               │
  • предупреждения о дефиците              │      ▼                               │
  • квитанция applied/error                │ App/exchange/ (новый пакет)          │
                                           │  • task registry                      │
 [Браузер оператора]                       │  • task store (web_outputs/exchange) │
  • страница /tasks/{task_id}/ui ─────────▶│  • contract JSON 1.1 / XML           │
    (существующий UI №16 в режиме задания) │  • подготовка снимка из invoice_model│
                                           │      │                               │
                                           │      ▼                               │
                                           │ JobStore → OCR → invoice_service     │
                                           │  (receipt_adapter / catalog / mapping)│
                                           └──────────────────────────────────────┘
```

Решения:

1. **Не переписывать существующий UI и OCR.** Задание 1С — надстройка:
   `task_id` связан с обычным `job_id`; страница задания — текущий интерфейс
   №16, открытый в режиме «задание из 1С».
2. **Новый пакет `App/exchange/`** (без правок бизнес-логики счёта):
   - `multipart.py` — разбор `multipart/form-data` для загрузки фото со
     страницы задания;
   - `store.py` — реестр заданий: `task_id`, `database_id`, `request_id`,
     `job_id`, `document_uuid`, версия, checksum, статусы; хранение
     `web_outputs/exchange/tasks/<task_id>/task.json` + снимки
     `result-vN.json`; блокировки и восстановление при старте;
   - `contract.py` — сборка JSON 1.1, канонический checksum
     (`sort_keys`, `separators=(",",":")`, UTF-8, без ASCII-экранирования —
     как `receipt_adapter._canonical`), запись XML (`ElementTree`);
   - `service.py` — сценарии: создать/найти задание, принять фото,
     подтвердить, выдать результат, принять квитанцию.
3. **Снимок 1С строится из `invoice_model()`**: документ счёта + строки
   `generation.items` + `approved_targets` + явные выборы оператора.
   Никакого повторного OCR или валидации чека не выполняется.
4. **Правила подтверждения:** `confirm` допустим только при `ready`
   (чек `finalized`, `validation_status = match`, все строки связаны, суммы
   сходятся). Иначе 409 с причинами — как блокировка в текущем UI.
5. **Неизменяемость:** после `confirm` снимок `result-vN.json` фиксируется;
   любая правка чека/выбора инвалидирует подтверждение (состояние `review`,
   `GET result` → 409) до нового подтверждения.
6. **Идентификаторы:** `task_id` — отдельный UUID (hex), `request_id` —
   из формы 1С, `database_id` — значение окружения
   `TORGSOFT_CATALOG_DATABASE_ID` (по умолчанию `local`; для «Алатау»
   согласовать, например `alatau`). `document_uuid` появляется только после
   записи через `document-link`/`import-receipt`.
7. **Один процесс обязателен**: реестр заданий и блокировки process-local,
   как у `JobStore`; `--workers` не использовать.

### 4.1. Маппинг снимка (invoice_model → контракт 1.1)

## 8. Риски и решения

| Риск | Решение |
|---|---|
| В stdlib-сервере нет готового multipart-парсера | Разбор через `email.parser` с лимитом размера; тесты на 1С-совместимый запрос |
| `ThreadingHTTPServer` и один процесс ограничивают параллелизм | Очередь OCR уже одна (`ThreadPoolExecutor(max_workers=1)`); задания 1С только добавляют лёгкие запросы |
| Расхождение цен: сумма строки в 1С = цена × количество (округление) | В снимке передаются `quantity/price/amount` как decimal-строки; 1С сверяет сумму строки, расхождение > допуска — блокирующая ошибка |
| В каталоге №16 нет UUID 1С | `uuid: null`, идентичность по коду/артикулу с проверкой уникальности в 1С (как в контракте) |
| Потеря реквизитов незаписанной формы 1С | Ручная команда «Восстановить задание по ID» (этап M5) |
| Повторная квитанция после сбоя | Хранить `operation_id` и тело; повтор идемпотентен, смена тела → 409 |
| Изменение чека после подтверждения | Версия инвалидируется, `GET result` → 409 до нового `confirm` |

## 9. Критерии приёмки интеграции

1. Из 1С создаётся задание; страница открывается; фото распознаётся.
2. Повтор «Обработать фото» открывает то же задание; второго не создаёт.
3. «Получить результат» до подтверждения → 202, форма не меняется.
4. После подтверждения снимок неизменяем; повторный GET отдаёт ту же версию
   и checksum.
5. Правка чека/выбора после подтверждения → 409 до повторного подтверждения.
6. 1С заполняет форму без записи; повторная загрузка не дублирует строки.
7. Запись счёта → связь сохранена, `applied` доставлен (в т.ч. после
   сбоя сети — повтором той же квитанции); заполнение без записи не даёт
   `applied`.
8. Пустой записанный счёт связывается через `document-link`, без `applied`.
9. Суммы строк и итог совпадают с проверенным чеком; дефицит — только
   предупреждение с тремя решениями.
10. Сквозной сценарий на тестовой базе 3.0.75.1 с реальным чеком.
